# Auth0 Setup — Complete Guide

> **Scope:** Full setup of Auth0 for this SaaS project, from account creation to Actions, covering both the **tenant platform** and the **admin backoffice portal**. Covers all applications, APIs, connections, social providers, and Actions in the correct order.

---

## Overview

This project uses **one Auth0 tenant** with **two entirely separate authentication surfaces**:

| Surface              | Users                        | Identity DB                                 | App                 | API Audience                     |
| -------------------- | ---------------------------- | ------------------------------------------- | ------------------- | -------------------------------- |
| **Platform**         | Tenant users (end-customers) | `Username-Password-Authentication` + Google | `SaaS Platform SPA` | `https://api.your-app.com`       |
| **Admin backoffice** | Internal admin staff only    | `Admin-Users-DB` (signup disabled)          | `SaaS Admin Portal` | `https://admin-api.your-app.com` |

Auth0 resources that will be created:

| #   | Type              | Name                               | Used by                                         |
| --- | ----------------- | ---------------------------------- | ----------------------------------------------- |
| 1   | API               | `SaaS Platform API`                | Platform backend — validates tenant JWTs        |
| 2   | API               | `SaaS Admin API`                   | Admin backend — validates admin JWTs            |
| 3   | Application (SPA) | `SaaS Platform SPA`                | Shell + Auth MFE (platform users)               |
| 4   | Application (SPA) | `SaaS Admin Portal`                | Admin standalone SPA (admin users)              |
| 5   | Application (M2M) | `SaaS Platform M2M`                | Backend — invite flow, user management          |
| 6   | Application (M2M) | `SaaS Admin CLI`                   | Scripts only — admin user provisioning          |
| 7   | DB Connection     | `Username-Password-Authentication` | Platform users (default, already exists)        |
| 8   | DB Connection     | `Admin-Users-DB`                   | Admin users only (signup disabled)              |
| 9   | Social Connection | `google-oauth2`                    | Platform users (Google login)                   |
| 10  | Passwordless      | `email`                            | Platform invite emails (passwordless link)      |
| 11  | Action            | `Account Linking`                  | Merges Google + passwordless same-email         |

| 13  | Action            | `Enrich Admin Access Token`        | Copies `email` + `name` into admin access token |
| 14  | Action            | `Enforce MFA for Admin`            | Requires MFA on every admin login               |

| Name                       | Type | Why it exists                                                                                                                                                                                 |

## Step 0 — Create Auth0 account and tenant

1. Go to [auth0.com](https://auth0.com) → **Sign Up** (free tier supports up to 7,500 MAU).
2. After email verification, Auth0 creates a default tenant (e.g., `dev-xxxxxxxx.us.auth0.com`).
3. (Optional but recommended) Create a **dedicated tenant** for this project:
   - Dashboard → top-left tenant dropdown → **Create Tenant**
   - Name: `your-company-saas` (this becomes `your-company-saas.eu.auth0.com`)
   - Region: choose the region closest to your users/servers (EU → `eu.auth0.com`, US → `us.auth0.com`)
4. Note your tenant domain: `{tenant}.{region}.auth0.com` — this becomes `AUTH0_DOMAIN` (used by both platform and admin, since it's the same tenant).

> **Tip for production:** create two tenants — one for `dev` / `staging` with lax settings, one for `prod` with stricter security policies. Follow the same steps twice.

## Step 5 — Actions

Actions run in the **Login flow** and are triggered on every login. All three actions added here are **Login flow** actions.

### 5a — Account Linking

Handles the case where the same user signs in via both Google and a passwordless email link. Auth0 creates two separate user records; this action merges them into one.

> This is typically provided as a ready-to-use Auth0 community action.  
> Check **Actions → Library → Explore** and search for "account linking" — Auth0 or the community may provide an up-to-date version.

If you write it yourself, the minimal version:

```javascript
const ManagementClient = require('auth0@3');

exports.onExecutePostLogin = async (event, api) => {
  if (!event.user.email_verified) return;

  const management = new ManagementClient({
    domain: event.secrets.AUTH0_DOMAIN,
    clientId: event.secrets.M2M_CLIENT_ID,
    clientSecret: event.secrets.M2M_CLIENT_SECRET,
  });

  const users = await management.users.getByEmail({ email: event.user.email });

  if (users.data.length <= 1) return; // no duplicates

  const primary = users.data.find((u) => u.user_id !== event.user.user_id);
  if (!primary) return;

  await management.users.link(
    { id: primary.user_id },
    {
      user_id: event.user.user_id,
      provider: event.user.identities[0].provider,
    },
  );
};
```

**Secrets for this Action:**
| Key | Value |
|---|---|
| `AUTH0_DOMAIN` | `{tenant}.{region}.auth0.com` |
| `M2M_CLIENT_ID` | Client ID of `SaaS Platform M2M` |
| `M2M_CLIENT_SECRET` | Client Secret of `SaaS Platform M2M` |

**Required npm module:** add `auth0` as a dependency in the Action editor.

**Scopes needed by this Action's M2M:** `read:users_by_email`, `update:users` (already granted above in Step 3c).

### 5b — Add Custom Claims (platform)

Auth0 access tokens do **not** include `email` by default. This action copies it into the JWT as a namespaced custom claim so the backend `JwtStrategy` can read the user's email without an extra Management API call.

This action runs for **platform logins only** — it skips the admin client.

```javascript
exports.onExecutePostLogin = async (event, api) => {
  // Skip admin logins — the Enrich Admin Access Token action handles those.
  const ADMIN_CLIENT_ID = event.secrets.ADMIN_CLIENT_ID;
  if (event.client.client_id === ADMIN_CLIENT_ID) return;

  const namespace = event.secrets.CLAIMS_NAMESPACE; // e.g. https://api.your-app.com/
  api.accessToken.setCustomClaim(`${namespace}email`, event.user.email);
};
```

**Secrets for this Action:**
| Key | Value | Env var |
|---|---|---|
| `CLAIMS_NAMESPACE` | `https://api.your-app.com/` | Maps to `AUTH0_CLAIMS_NAMESPACE` (or `AUTH0_AUDIENCE` if not set) |
| `ADMIN_CLIENT_ID` | Client ID of `SaaS Admin Portal` | — (guard only, not an env var) |

> **Namespace convention:** must be a URL and must end with `/`. The backend reads the claim as `{namespace}email`.  
> The default fallback in `auth.config.ts` is `AUTH0_AUDIENCE` which already ends with `/` if set to `https://api.your-app.com`.  
> For clarity, set `AUTH0_CLAIMS_NAMESPACE=https://api.your-app.com/` explicitly.

### 5c — Enrich Admin Access Token

Adds `email` and `name` to the admin JWT. Runs for admin logins only (guarded by `client_id`).

```javascript
exports.onExecutePostLogin = async (event, api) => {
  const ADMIN_CLIENT_ID = event.secrets.ADMIN_CLIENT_ID;

  // Only enrich tokens issued for the admin SPA.
  if (event.client.client_id !== ADMIN_CLIENT_ID) return;

  const namespace = event.secrets.CLAIMS_NAMESPACE; // https://admin.saas-api.com/
  api.accessToken.setCustomClaim(`${namespace}email`, event.user.email);

  if (event.user.name) {
    api.accessToken.setCustomClaim(`${namespace}name`, event.user.name);
  }
};
```

**Secrets for this Action:**
| Key | Value | Env var |
|---|---|---|
| `ADMIN_CLIENT_ID` | Client ID of `SaaS Admin Portal` | — |
| `CLAIMS_NAMESPACE` | `https://admin.saas-api.com/` | `ADMIN_AUTH0_CLAIMS_NAMESPACE` (must match exactly, trailing slash required) |

### 5d — Enforce MFA for Admin

Forces every admin user to complete MFA on login. MFA is enforced at the Auth0 Action level — there is **no MFA code in the application** (backend or frontend).

```javascript
exports.onExecutePostLogin = async (event, api) => {
  const ADMIN_CLIENT_ID = event.secrets.ADMIN_CLIENT_ID;

  // Only enforce MFA for the admin portal.
  if (event.client.client_id !== ADMIN_CLIENT_ID) return;

  // If the user hasn't completed MFA in this session, challenge them.
  if (event.authentication?.methods?.some((m) => m.name === 'mfa')) return;

  api.multifactor.enable('any', { allowRememberBrowser: false });
};
```

**Secrets for this Action:**
| Key | Value |
|---|---|
| `ADMIN_CLIENT_ID` | Client ID of `SaaS Admin Portal` |

**Options:**

- `allowRememberBrowser: false` — requires MFA on every login (no "trust this device" option). Set to `true` if you want to allow 30-day browser trust.
- `'any'` — lets the user choose from any enrolled MFA factor (TOTP authenticator app, SMS, etc.).

**First admin login flow:** on first login, Auth0 will redirect the admin to the MFA enrollment screen (authenticator app, SMS, etc.) before issuing the access token. Subsequent logins will require them to complete the MFA challenge.

> MFA enrollment data is stored in Auth0, not in the `admin_users` legal DB table.

## Step 6 — Login Flow Composition

**Actions → Flows → Login**

Add all four actions to the Login flow in this exact order:

```
[Start] ──► [Account Linking] ──► [Add Custom Claims] ──► [Enrich Admin Access Token] ──► [Enforce MFA for Admin] ──► [Complete]
```

**Why this order:**

1. **Account Linking** first — merges duplicate users before any claims are set, so subsequent actions always see the primary user identity.
2. **Add Custom Claims** second — adds `email` claim for platform logins. Skip guard ensures it no-ops for admin.
3. **Enrich Admin Access Token** third — adds `email` + `name` for admin logins. Skip guard ensures it no-ops for platform users.
4. **Enforce MFA for Admin** last — challenges the admin with MFA after claims are enriched. Must run after enrichment so the session is already identified as an admin. Skip guard ensures it no-ops for platform users.

To add actions to the flow: drag each action from the right panel onto the flow canvas, position them between Start and Complete, then click **Apply**.

### Connections

- [ ] `Admin-Users-DB` enabled **only** on `SaaS Admin Portal`

- [ ] `SaaS Admin API` authorized on `SaaS Admin Portal`
- [ ] `Auth0 Management API` authorized on `SaaS Platform M2M` with 4 scopes
- [ ] `Auth0 Management API` authorized on `SaaS Admin CLI` with 5 scopes

### Actions

- [ ] All four actions are **Deployed** (not just saved)
- [ ] Login flow order: Account Linking → Add Custom Claims → Enrich Admin Access Token → Enforce MFA for Admin
- [ ] `Account Linking` secret `M2M_CLIENT_ID` points to `SaaS Platform M2M`
- [ ] `Add Custom Claims` secret `ADMIN_CLIENT_ID` points to `SaaS Admin Portal` (not platform SPA)
- [ ] `Enrich Admin Access Token` secret `ADMIN_CLIENT_ID` points to `SaaS Admin Portal`
- [ ] `Enrich Admin Access Token` secret `CLAIMS_NAMESPACE` ends with `/` and matches `ADMIN_AUTH0_CLAIMS_NAMESPACE` in `.env`
- [ ] `Enforce MFA for Admin` secret `ADMIN_CLIENT_ID` points to `SaaS Admin Portal`

### Applications to delete (cleanup)

Auth0 auto-creates several apps. After extracting credentials, decide what to keep:

- [ ] `Default App` — delete (auto-generated placeholder, unused)
- [ ] `SaaS Platform API (Test Application)` — delete, **or reuse as `SaaS Platform M2M`** (add Management API scopes)
- [ ] `SaaS Admin API (Test Application)` — delete, **or reuse as `SaaS Admin CLI`** (add Management API scopes)

Keep as-is (do not delete):

- `SaaS Platform SPA` — platform SPA
- `SaaS Admin Portal` — admin SPA
- `SaaS Platform M2M` (or the reused Test Application)
- `SaaS Admin CLI` (or the reused Test Application)
- `API Explorer Application` — keep; auto-managed by Auth0 Dashboard
- `SaaS App Action` — **do not delete**; Auth0 created this for the Account Linking Action's Management API calls. Deleting it will break the action.
